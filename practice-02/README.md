## 4. Модель данных и функции

**Поля задачи:**

```js
{
  id: 20,
  title: "Подготовить демонстрацию",
  completed: false,
  priority: "medium"
}
```

| Поле        | Правило                                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`        | Число, положительное безопасное целое: `Number.isSafeInteger(id) && id > 0`. Строка `"4"`, `1.5`, `NaN`, `Infinity`, `null` и `undefined` отклоняются.                   |
| `title`     | Строка. После `trim()` длина от 1 до 100 включительно. В объект записывается очищенная строка; внутренние пробелы сохраняются. Не-строки отклоняются до вызова `trim()`. |
| `completed` | Логическое значение. При создании новой задачи всегда `false`. `"false"`, `0`, `null` не принимаются в `setTaskCompleted`.                                               |
| `priority`  | Строго `"low"`, `"medium"` или `"high"`. По умолчанию `"medium"`.                                                                                                        |

**Назначение файлов:**

| Файл                                   | Ответственность                                                                                                                         |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `src/data.js`                          | Экспорт `demoTasks`, `variantTasks`, `variantNumber`. Данные без функций и вывода.                                                      |
| `src/task-service.js`                  | Девять прикладных функций, проверки полей, копирование. Без `console.log`, без импорта `demoTasks`, без глобального изменяемого списка. |
| `src/main.js`                          | Импорт модулей, последовательность действий, вывод, обработка отказов.                                                                  |
| `examples/functions-and-references.js` | Шесть независимых экспериментов к заданию 1.                                                                                            |
| `checks.js`                            | 35 именованных проверок через `node:assert/strict`.                                                                                     |

**Контракты операций:**

| Функция            | Успех                                     | Ошибка                 |
| ------------------ | ----------------------------------------- | ---------------------- |
| `createTask`       | `{ ok: true, task }`                      | `{ ok: false, error }` |
| `findTaskById`     | найденный объект                          | `undefined`            |
| `getPendingTasks`  | новый массив                              | —                      |
| `getTaskTitles`    | новый массив строк                        | —                      |
| `getTaskStats`     | `{ total, completed, pending, progress }` | —                      |
| `addTask`          | `{ ok: true, tasks: новыйМассив }`        | `{ ok: false, error }` |
| `setTaskCompleted` | `{ ok: true, tasks: новыйМассив }`        | `{ ok: false, error }` |
| `renameTask`       | `{ ok: true, tasks: новыйМассив }`        | `{ ok: false, error }` |
| `removeTask`       | `{ ok: true, tasks: новыйМассив }`        | `{ ok: false, error }` |

**Почему `id` не равен индексу:** индекс показывает текущее место в массиве и меняется после удаления соседнего элемента; `id` идентифицирует запись и в модели ПР2 не меняется. В `demoTasks` задача с `id = 4` лежит под индексом `1`, поэтому поиск `tasks[id]` дал бы неверную запись. Для поиска используется `find` со строгим сравнением `task.id === id`, и строка `"4"` числу `4` не равна.

**Почему `getTaskStats` возвращает число, а не строку с процентом:** функция вычисляет значение, а форматирование — задача отображения. `progress.toFixed(1)` вызывается в `main.js`, где и решается, как показать результат. Случай пустого списка обрабатывается отдельной ветвью до деления, поэтому `NaN` не появляется; в самой сводке для пустого списка `progress` равен `0`.

**Какие объекты копируются при изменении задачи:** создаётся новый массив (`[...]`, `map`, `filter`) **и** новый объект изменяемой записи (`{ ...task, completed }` или `{ ...task, title }`). Неизменённые записи переиспользуются. Одного нового массива недостаточно: если записать `tasksCopy[0].completed = true`, изменится исходный объект, потому что в новом массиве лежат ссылки на те же самые объекты.

## 9. Вывод

**Функции вместо линейного кода.** В ПР1 расчёты выполнялись прямо в файле над отдельными переменными. Здесь девять прикладных функций возвращают данные, а вывод выполняет демонстрационный сценарий. Это видно на `getTaskStats`: она возвращает число `progress`, а `toFixed(1)` вызывается в `main.js`. `console.log()` внутри прикладной функции не заменяет `return` — следующей операции нужно значение, а не сообщение.

**Объекты и массивы вместо отдельных переменных.** Появилась модель задачи с четырьмя полями и операции над списком. Стало видно, что `const` не делает объект неизменяемым, а `[...tasks]` создаёт новый массив, но сохраняет ссылки на объекты внутри. Поэтому при изменении записи создаётся и новый массив (`map`), и новый объект изменяемой записи (`{ ...task, completed }`). Одного нового массива недостаточно: если записать `tasksCopy[0].completed = true`, изменится исходный объект. Именно поэтому одного условия `result.tasks !== tasks` недостаточно для доказательства отсутствия мутации — нужна проверка полей каждого объекта, что и делают проверки 33 и 34.

**Разделение ответственности через модули.** `task-service.js` не знает про `demoTasks` и не пишет в консоль — он получает массив параметром. Это позволяет проверять его на любом корректном наборе: проверка 35 использует другой массив, а сценарий варианта 2 — `variantTasks`. В ПР3 та же логика подключится к DOM без переписывания.

**Наиболее показательная ошибка.** Эксперимент 2: стрелочная функция с телом в фигурных скобках и без `return` вернула `undefined`, хотя выражение `value * value` вычислялось. Та же ошибка возможна в `map((task) => { task.id === id ? { ...task, completed } : task })` — без `return` получился бы массив `undefined`, и всё дальнейшее чтение упало бы. Поэтому в `map` и `filter` callback-функции записаны либо в краткой форме, либо с явным `return`.

**Вторая полезная ошибка** — выбор способа обновления записи. Если бы в `setTaskCompleted` использовался `tasks[foundIndex].completed = completed`, проверки 23 и 33 сразу показали бы мутацию входных данных. Переход на `map` + spread решил проблему без дополнительных проверок.
