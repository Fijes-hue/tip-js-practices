## 3. Реализация

### 3.1. HTTP-клиент

requestJson(path, { method, query, body, signal, timeoutMs }) поддерживает GET, POST, PATCH, DELETE. Неизвестные методы и GET с телом отклоняются с TypeError до сетевого запроса. Метод нормализуется в верхний регистр.

Заголовки формируются минимально: Accept: application/json добавляется всегда; Content-Type: application/json — только при наличии тела. Тело сериализуется через JSON.stringify. Такой подход не вызывает лишних CORS preflight у GET-запросов.

Порядок обработки ответа: сначала response.ok, затем 204 → null, затем проверка Content-Type и разбор JSON. Сетевой try отделён от обработки Response, чтобы HTTP-ошибка не превратилась в network.

### 3.2. Доменный API

- getTasks(filters, options) -> { tasks, meta };
- getTaskById(id, options) -> task;
- getCategories(options) -> category[];
- loadInitialData(filters, options) -> { tasks, categories, meta } через Promise.all;
- createTask(draft, options) -> POST /tasks;
- updateTask(id, changes, options) -> PATCH /tasks/:id;
- setTaskCompleted(id, completed, options) -> PATCH /tasks/:id;
- deleteTask(id, options) -> DELETE /tasks/:id, ожидает null;
- resetDemoData(options) -> POST /debug/reset.

### 3.3. Состояния интерфейса

- loading — aria-busy="true" на панели, сообщение о загрузке;
- ready — карточки и число найденных задач;
- empty — запрос успешен, но результатов нет; карточки не выводятся;
- error — понятное сообщение и кнопка повтора.

### 3.4. Изменение данных

На время мутации блокируются кнопки формы, сброса и действий карточек — двойной щелчок не создаст два одинаковых запроса. После успешной мутации список повторно запрашивается с сервера: currentTasks содержит только подтверждённое сервером состояние, локальные изменения не применяются.

Если редактируемая задача исчезла из текущей выборки (например, была удалена или отфильтрована), форма автоматически возвращается в режим создания.

### 3.5. Защита от устаревшего ответа

Использованы два механизма одновременно:

перед новой загрузкой вызывается activeController.abort() — предыдущий запрос отменяется;

каждой загрузке присваивается номер sequence, и applySuccessfulLoad / applyFailedLoad применяют результат только при sequence === loadSequence.

Вторая проверка нужна даже при отмене: если тестовый клиент или кэш завершит операцию до реакции на сигнал, старый ответ не перезапишет новый фильтр.

Отмена — не пользовательская ошибка. В applyFailedLoad есть проверка error.kind === "aborted"; при ней состояние не меняется, сообщение не показывается.

## 6. Ответы на контрольные вопросы

1. _Почему `fetch` не отклоняет Promise при ответе 404?_
   fetch отклоняет Promise только при сетевой ошибке (DNS, отказ соединения, отмена) или некорректном URL. Ответ с любым HTTP-статусом, включая 404 и 500, считается успешно полученным ответом. Поэтому проверка response.ok выполняется явно, а 404 обрабатывается как ApiError с kind: "http"
2. _Почему ответ 204 нельзя разбирать вызовом `response.json()`?_
   204 No Content не имеет тела. response.json() на пустом теле выбросит SyntaxError. Поэтому клиент возвращает null до проверки Content-Type и разбора — это часть контракта DELETE.
3. _Чем состояние `empty` отличается от `error`?_
   empty — запрос завершился успешно, но вернул пустой массив. Это нормальный результат фильтрации. error — запрос не выполнен: сеть, тайм-аут, HTTP-ошибка или неверный формат. Пользователю показываются разные сообщения, а кнопка повтора появляется только в error.
4. _Зачем отменять предыдущий запрос при смене фильтров?_
   Первый запрос может завершиться позже второго, и его ответ перезапишет новый список. AbortController.abort() прекращает сетевую операцию, а sequence-номер дополнительно отбрасывает устаревший ответ, если он всё же пришёл.
5. _Почему после мутации список повторно запрашивается у API?_
   Сервер — единственный источник истины. Локальная копия могла бы разойтись с сервером, если сервер изменил данные (например, назначил id, поменял completed или отклонил часть полей). Повторный GET с текущими фильтрами гарантирует, что отображается подтверждённое сервером состояние.
