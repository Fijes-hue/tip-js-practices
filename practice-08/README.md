## Полученный результат

React-приложение загружает задачи и категории с учебного API, передаёт фильтры в query-параметрах, выполняет POST, PATCH и DELETE, повторяет GET после подтверждённой мутации. Данные хранятся в памяти процесса API: перезагрузка страницы их сохраняет, перезапуск сервера возвращает исходный набор из 12 задач.

Состояние разделено по назначению:

- `snapshot` — последний успешный ответ сервера;
- `status` — `loading`, `ready` или `error`;
- `error` — ошибка загрузки или `null`;
- `mutationError` — ошибка последней мутации;
- `pending` — идёт ли мутация.

Начальный фильтр варианта 8 — `{ completed: 'false', priority: 'high', categoryId: '2' }`; на старте 2 задачи из 12.

## Архитектура

| Слой                   | Ответственность                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `api-client.js`        | Транспорт: методы, JSON-тело, статусы 201/204, `ApiError`, тайм-аут и отмена             |
| `task-api.js`          | Маршруты задач и категорий, проверка схемы ответа, `loadInitialData` через `Promise.all` |
| `hooks/useTaskData.js` | Эффект загрузки, cleanup, блокировка повторной мутации, повторный GET                    |
| `App.jsx`              | Хранит `filters` и снимок редактируемой записи; связывает хук и компоненты               |
| `components/*`         | Представление без побочных эффектов                                                      |

**Зависимости эффекта загрузки:** `api`, `q`, `completed`, `priority`, `categoryId`, `revision`. `api` создан в `config.js` вне компонента — ссылка стабильна. `snapshot` в зависимости не входит: это результат загрузки, включение вызвало бы бесконечный цикл.

**Cleanup:** помечает локальный флаг `active` неактивным и вызывает `controller.abort()`. Проверка `active` в `catch` и `try` не даёт устаревшему ответу изменить состояние, даже если отмена проигнорирована.

**Служебные ref:** `mountedRef` — чтобы после размонтирования не вызывать `setState`; `mutationControllerRef` — блокировка двойного клика: ссылка устанавливается **до** первого `await` и освобождается в `finally` только для своего контроллера.

## Загрузка и изменения

**Старые ответы.** Каждый запуск эффекта создаёт собственный `AbortController` и флаг `active`. В `cleanup` запрос отменяется, флаг снимается. Перед записью в `setState` в обеих ветках — успех и ошибка — проверяется `active` и `controller.signal.aborted`. Поэтому запоздавший ответ не заменяет свежий список и не показывает ложную ошибку.

**Повторная мутация.** В `state` `pending` недостаточно: два синхронных клика успевают прочитать `false` до первого `setPending(true)`. Поэтому блокировка держится в `mutationControllerRef`: ссылка на текущий контроллер устанавливается до `await`. Второй вызов видит `ref !== null` и сразу возвращает `false`.

**Ошибка POST и ошибка последующего GET.** Разделены: `saveTask` ждёт `api.createTask`, при успехе возвращает `true` и инкрементирует `revision`. Увеличение `revision` заставляет эффект выполнить новый GET. Если сам GET упал — `error` пополнится, `status` станет `error`, но `saveTask` останется `true` и `mutationError` не установится. Это отражает факт: изменение на сервере подтверждено, не удалось только показать обновлённый список.

**Черновик при ошибке.** `TaskForm` очищает поля только при `onSave(...) === true`. При `false` значения остаются в форме, `mutationError` выводится в `App` отдельным сообщением, пользователь может исправить данные и повторить.

## Вывод

В ходе работы React-приложение подключено к учебному HTTP API. Реализован хук useTaskData, который загружает данные в useEffect, отменяет устаревшие запросы и игнорирует запоздавшие ответы. Операции изменения выполняются через общий mutate: блокировка повторного вызова — через useRef до первого await, при успехе увеличивается revision и запускается новый GET с актуальными фильтрами.
