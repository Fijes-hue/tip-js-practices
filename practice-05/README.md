## Организация кода

Кратко описать ответственность файлов:

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API: маршруты /tasks, /categories, /health, отладочные сценарии. Не изменяется |
| `src/api-client.js` | Транспорт: buildUrl, createApiClient, requestJson, класс ApiError, классификация ошибок, тайм-аут и отмена. Не знает про задачи |
| `src/task-api.js` | Предметный клиент: маршруты задач и категорий, нормализация фильтров, проверка схемы ответа |
| `src/variant.js` | Конфигурация индивидуального варианта: номер и объект фильтров |
| `src/main.js` | Консольный контрольный сценарий: вызывает loadInitialData, печатает таблицу задач и обрабатывает отказ |

fetchFn передаётся в createApiClient аргументом, чтобы модуль можно было проверить с подменённой функцией без реальной сети и без подмены глобального fetch. HTTP-ошибки проверяются отдельно от сетевых, потому что fetch не отклоняется на 4xx/5xx: это нормальный ответ сервера, а не отказ сети. Один общий try вокруг fetch и вокруг обработки Response превратил бы 404 в network. JSON после разбора проверяется по контракту, потому что JSON.parse подтверждает только синтаксис, а не схему: {"data":"не массив"} — валидный JSON, но неверный ответ.

Правила проверки:
- Задача: id — положительное безопасное целое; title — строка 1–100 после trim; completed — boolean; priority ∈ {low, medium, high}; categoryId — положительное целое
- Категория: id — положительное целое; name — строка 1–100
- Уникальность: повторяющиеся id в коллекции отклоняются
- meta.total: должен совпадать с длиной data; иначе invalid-response

## Последовательная и параллельная загрузка

Сравнить два сценария получения задач и категорий через `/debug/delay`. Каждый сценарий выполнить минимум три раза с одинаковыми задержками.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 210 | 205 | 208 | Время суммируется, потому что второй запрос стартует после первого |
| `Promise.all` | 110 | 105 | 108 | Время примерно равно одной задержке, потому что оба запроса стартуют до общего ожидания |

Причинная связь: Promise.all не создаёт параллельность сам, но оба запроса уже запущены до await, поэтому их таймеры идут одновременно. Значения зависят от машины и не сравниваются с чужими.

## Собственные проверки

| № | Исходное состояние и действие | Ожидаемый результат | Фактический результат | Итог |
|---:|---|---|---|---|
| 1 | Вызвать getTasks({ categoryId: 3, q: "API & отчёт" }) через подменённый fetchFn, зафиксировать URL | URL содержит categoryId=3 и q=API+%26+%D0%BE%D1%82%D1%87%D1%91%D1%82; результат — нормализованный { tasks, meta } | Совпадает | Пройдено |
| 2 | Подменить fetchFn так, чтобы вернуть Response со статусом 500 и телом {"error":{"code":"INTERNAL","message":"Сбой"}} | ApiError, kind: "http", status: 500, code: "INTERNAL", message: "Сбой" | Совпадает | Пройдено |
| 3 | Запустить requestJson("/debug/delay", { query: { ms: 200 }, timeoutMs: 20 }), затем повторить с внешним AbortController до истечения тайм-аута | Первый: kind: "timeout"; второй: kind: "aborted"; cause instanceof Error в обоих случаях | Совпадает | Пройдено |

Проверка 1 дополняет готовый набор: здесь используется нестандартная комбинация categoryId + q со специальным символом & в строке. Подтверждает, что кодирование не делается вручную и false/0 не теряются.

Проверка 2 покрывает код 500, которого нет в готовых тестах (там 404, 400, 503). Показывает, что HTTP-ошибка не маскируется под network.

Проверка 3 проверяет различие timeout и aborted в одном сценарии — важно, потому что оба используют AbortError и легко спутать.

## Отладка

Точки останова:

- В requestJson перед fetchFn(...) — фиксируем url, method, заголовки, signal.aborted;

- После получения response — response instanceof Response, response.status, response.ok, Content-Type;

- Перед response.json() — что предыдущие проверки пройдены;

- В ветке catch вокруг fetchFn — какая именно ошибка пришла и был ли signal.aborted.

Успешный запрос getTaskById(25):

|---|---|
| url | http://127.0.0.1:5505/api/tasks/25 |
| response.status | 200 |

| Content-Type | application/json; charset=utf-8 |
| payload | { data: { id: 25, ... } } |

## Вывод

В ходе работы реализован клиент для получения данных с локального HTTP API: общий транспорт в api-client.js и предметный модуль задач в task-api.js. Общий клиент не знает про задачи, а предметный не вызывает fetch — это разделение позволяет позже подключить клиент к DOM-интерфейсу без переписывания транспорта.
