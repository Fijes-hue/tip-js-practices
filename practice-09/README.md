## Цель и результат

**Цель** — самостоятельно реализовать HTTP-сервер на Node.js и Express, воспроизводящий часть контракта учебного API из ПР6/ПР8: чтение задач и категорий с фильтрацией, корректную обработку ошибок и поддержку методов GET/HEAD/OPTIONS.

**Фактически реализовано:**

- четыре GET-маршрута (`/health`, `/categories`, `/tasks`, `/tasks/:id`);
- полная валидация query-параметров с отклонением неизвестных имён, дубликатов, неверных значений;
- строгая проверка id (регулярка `/^[1-9]\d*$/` + `Number.isSafeInteger`);
- поиск по названию без учёта регистра (`toLocaleLowerCase('ru-RU')`);
- ответы 400 `INVALID_QUERY` / `INVALID_ID`, 404 `TASK_NOT_FOUND` / `ROUTE_NOT_FOUND`, 405 `METHOD_NOT_ALLOWED` с заголовком `Allow`;
- HEAD-запросы (Express автоматически отдаёт заголовки без тела для GET-маршрутов);
- OPTIONS 204 с CORS-заголовками;
- 500 `INTERNAL_ERROR` без утечки стека и внутреннего текста ошибки.

Данные хранятся в памяти процесса. Операции записи (POST, PATCH, DELETE) не реализованы — это граница этапа ПР9, которая будет снята в ПР10.

## Реализация

**Распределение обязанностей модулей:**

| Модуль            | Обязанности                                                                                                                  | Не делает                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `validation.js`   | `parsePositiveId` (строгая регулярка + `isSafeInteger`), `parseFilters` (проверка имён, дубликатов, преобразование значений) | Читать `req`, отправлять `res`  |
| `task-service.js` | `selectTasks` (фильтрация через AND), `findTask` (поиск по id, не по индексу)                                                | Знать HTTP-статусы              |
| `store.js`        | Хранит копии данных для каждого экземпляра приложения                                                                        | Формировать HTTP-ответы         |
| `routes.js`       | Связь маршрутов с `store` и `validation`, формирование ответов                                                               | Хранить глобальный массив задач |
| `app.js`          | Сборка middleware: общие заголовки, OPTIONS, router, 404, обработчик ошибок                                                  | Открывать порт                  |
| `server.js`       | Чтение порта, запуск `listen`                                                                                                | Реализовывать фильтры           |

**Нормализация `false`.** Строка `'false'` в JavaScript имеет истинностное значение `true` (`Boolean('false') === true`). Поэтому статус проверяется явным сравнением: `raw === 'true'` даёт `true`, `raw === 'false'` даёт `false`, всё остальное отклоняется как `INVALID_QUERY`.

**Контроль дубликатов query.** Express представляет query как объект, и при наличии `?q=a&q=b` в нём остаётся только последнее значение. Чтобы обнаружить повторения, используется `searchParams.getAll(name)` на оригинальном `URLSearchParams`, построенном из `req.originalUrl`. Если длина массива значений больше 1 — бросается `ApiError(400, 'INVALID_QUERY')`.

**Проверка id.** Используется цепочка:

1. регулярка `/^[1-9]\d*$/` — отсекает `0`, `-1`, `01`, `4abc`, `1.5`, пробелы;
2. `Number(raw)` — преобразование;
3. `Number.isSafeInteger(value)` — защита от чисел больше `Number.MAX_SAFE_INTEGER` (`9007199254740992` отклоняется).

Одного `parseInt` недостаточно: он принимает начало строки `4abc` как `4`.

**Порядок middleware в `app.js`:**

1. Общие заголовки + ранний ответ на `OPTIONS` (204 без тела);
2. `router` с GET-маршрутами;
3. внутри `router` — `router.all` для четырёх известных путей, отдающий 405 с заголовком `Allow: GET, HEAD, OPTIONS`;
4. обработчик неизвестного пути (404 `ROUTE_NOT_FOUND`);
5. обработчик ошибок (4 аргумента) — последним.

Такой порядок гарантирует: OPTIONS отвечает до маршрутов, GET-запросы доходят до своих обработчиков, 405 срабатывает только для известных путей с неподходящим методом, а неизвестные пути получают 404.

## Контрольные вопросы

**1. Чем JavaScript в Node.js отличается от JavaScript в браузере?**
В Node.js нет DOM, `window`, `document`, `localStorage` и браузерных API. Вместо них доступны модули `node:fs`, `node:http`, `node:path`, файловая система, сетевые сокеты. Код выполняется в одном потоке с event loop, но асинхронные операции делегируются системным вызовам. Модули ES импортируются через `import`, но с расширением `.js` в путях.

**2. Что определяет выбор маршрута: путь, query или HTTP-метод?**
Путь и HTTP-метод совместно. Express сопоставляет `req.method` и `req.path` с зарегистрированными обработчиками. Query-параметры (`?key=value`) не влияют на выбор маршрута — они разбираются внутри обработчика. `/tasks` и `/tasks?q=API` попадают в один и тот же маршрут.

**3. Чем `req.params` отличается от query-параметров?**
`req.params` — это части пути, заданные в маршруте через `:name` (например, `:id` в `/tasks/:id`). Они обязательны для совпадения маршрута и доступны как свойства объекта. Query-параметры (`?key=value`) не являются частью пути, не влияют на маршрутизацию и доступны через `req.query` (или ручной разбор `URLSearchParams`). В ПР9 query разбирается вручную, чтобы обнаружить дубликаты.

**4. Почему строка `'false'` требует явного преобразования?**
В JavaScript `Boolean('false') === true` — любая непустая строка истинна. Если преобразовывать наивно, фильтр `completed=false` в URL даст `true` на сервере, и клиент получит противоположный результат. Явное сравнение `raw === 'true'` / `raw === 'false'` гарантирует корректное преобразование и отклоняет все другие значения.

**5. Зачем проверять весь id и `Number.isSafeInteger`?**
`parseInt('4abc')` вернёт `4`, хотя строка не является числом. Регулярка `/^[1-9]\d*$/` отсекает такие случаи, а также `0`, `-1`, `01`, `1.5`, пробелы. `Number.isSafeInteger` защищает от чисел за пределами `Number.MAX_SAFE_INTEGER` (`9007199254740992`) — для них арифметика теряет точность, и id может совпасть с другим.

**6. Почему пустая выборка имеет статус 200, а отсутствующая задача — 404?**
Список `/api/tasks` — это коллекция. Запрос коллекции с фильтром, под который ничего не подходит, — это успешный запрос, вернувший пустой результат (как `SELECT * WHERE ...` без строк). `/api/tasks/:id` — запрос конкретного ресурса; если его нет, ресурс не найден (404). Это стандартная семантика REST: 404 означает «ресурс не существует», а не «ничего не найдено по фильтру».

**7. В чём различие `TASK_NOT_FOUND` и `ROUTE_NOT_FOUND`?**
`TASK_NOT_FOUND` (404) — путь корректный (`/api/tasks/999`), но ресурс с таким id отсутствует в данных. `ROUTE_NOT_FOUND` (404) — путь не соответствует ни одному зарегистрированному маршруту (`/api/missing`, `/api/tasks/4/extra`). Первый означает «запрос понятен, данных нет», второй — «такого endpoint не существует».

**8. Чем 405 отличается от 404 и зачем нужен `Allow`?**
404 — путь не существует. 405 — путь существует, но метод не поддерживается (например, `POST /api/tasks`, когда разрешены только GET/HEAD/OPTIONS). Заголовок `Allow: GET, HEAD, OPTIONS` сообщает клиенту, какие методы можно использовать. Это позволяет клиенту автоматически скорректировать запрос, а не гадать.

**9. Что означает `meta.total` при активных фильтрах?**
`meta.total` — размер возвращённой выборки, а не всего хранилища. При фильтре `completed=true` и 5 найденных задачах `total: 5`, хотя всего в базе 12. Надпись «Всего задач в системе: 5» для этого значения была бы некорректной. Клиент должен использовать `meta.total` для отображения «Найдено: 5», а не общего размера базы.

**10. Как порядок middleware влияет на результат?**
Express выполняет middleware последовательно. Если 404-обработчик стоит до router, все запросы завершатся 404, не дойдя до маршрутов. Если `router.all('/tasks')` стоит до `router.get('/tasks')`, он перехватит GET-запросы. Обработчик ошибок (4 аргумента) должен быть последним, иначе он не получит исключения из предыдущих middleware. Правильный порядок: общие заголовки → router с GET → router.all для 405 → 404 → обработчик ошибок.

**11. Почему обработчик ошибок имеет четыре параметра?**
Express распознаёт обработчик ошибок по сигнатуре `(error, req, res, next)` — четыре аргумента. Обычный middleware имеет три. Если указать три параметра, Express будет считать его обычным middleware и не передаст ему ошибки. Это соглашение фреймворка, а не опечатка.

**12. Зачем фабрика приложения отделена от открытия порта?**
`createApp()` возвращает настроенное Express-приложение без привязки к порту. Это позволяет тестам запускать сервер на свободном порту (`listen(0)`), выполнять проверки и закрывать его. Если бы порт открывался при импорте `app.js`, тесты конфликтовали бы с ручным запуском, а параллельные тесты мешали бы друг другу. `server.js` — это отдельный файл, который импортирует фабрику и запускает сервер на нужном порту.

**13. Какие данные допустимо отправлять клиенту при внутренней ошибке?**
Только общее сообщение «Внутренняя ошибка API.» и код `INTERNAL_ERROR`. Стек исключения (`error.stack`), внутренние сообщения, имена файлов и значения переменных раскрывать нельзя — это утечка информации о реализации. В тестах ПР9 проверяется, что строка `INTERNAL_SECRET` из тестового исключения не попадает в JSON-ответ.

**14. Почему CORS не является авторизацией?**
CORS — это механизм браузера, который решает, разрешить ли JavaScript-коду с одного origin читать ответ с другого origin. Он не мешает прямым HTTP-запросам из `curl`, Postman или другого сервера. Заголовок `Access-Control-Allow-Origin: *` означает «браузерный JavaScript с любого сайта может читать этот ответ», но не даёт никаких прав на изменение данных. Авторизация (токены, сессии) — отдельный слой, которого в ПР9 нет.

**15. Какие изменения потребуются в ПР10 для подключения всех действий клиента ПР8?**

- В `routes.js` добавить маршруты `POST /tasks`, `PATCH /tasks/:id`, `DELETE /tasks/:id`.
- Реализовать чтение JSON-тела запроса (middleware `express.json()` или ручной разбор).
- Валидировать поля создания и редактирования (title, priority, categoryId, completed).
- Назначать id при создании и хранить счётчик `nextId`.
- Обновить заголовок `Allow` в 405-обработчиках, добавив POST/PATCH/DELETE.
- Возможно, добавить `POST /debug/reset` для тестов.
- В `app.js` подключить `express.json()` до router.

## Вывод

В ПР9 реализован собственный HTTP-сервер на Express, воспроизводящий контракт учебного API для операций чтения. Ключевые освоенные идеи:

- **Разделение ответственности**: `validation.js` не знает про HTTP, `task-service.js` не знает про Express, `routes.js` связывает их и формирует ответы, `app.js` собирает middleware, `server.js` открывает порт.
- **Порядок middleware критичен**: OPTIONS отвечает первым, GET-маршруты идут до 405, 404 замыкает router, обработчик ошибок стоит последним.
- **Фабрика приложения (`createApp`)** позволяет тестам запускать изолированные экземпляры на свободных портах, не конфликтуя с ручным запуском.
- **Строгая валидация id**: регулярка + `Number.isSafeInteger` вместо наивного `parseInt` защищает от `4abc`, `01`, `9007199254740992`.
- **Явное преобразование `false`**: `Boolean('false') === true`, поэтому нужно сравнивать со строками `'true'`/`'false'`.
- **Дубликаты query** обнаруживаются через `searchParams.getAll()`, а не через `req.query`, который теряет повторения.
