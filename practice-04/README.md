## Организация кода

`task-service.js` — неизменяющие операции над задачами: создание, поиск, изменение, удаление. Без DOM и localStorage.
`form-validation.js` — чистая проверка черновика формы. Не знает про DOM.
`task-storage.js` — схема хранения, JSON и обработка ошибок хранилища. Принимает storage аргументом.
`task-view.js`— создание карточек, списка, сводки и пустого состояния.
`main.js` — состояние, режим формы, события, координация сервиса, хранения и отображения.

Функции хранения получают storage аргументом, чтобы их можно было проверить с объектом-имитацией и явно видеть внешнюю зависимость. Данные из JSON проверяются до использования, потому что JSON.parse подтверждает только синтаксис, а не схему.

## Вывод

В ходе работы приложение из ПР3 было расширено формой создания и редактирования задач, двумя уровнями проверки ввода и сохранением состояния в `localStorage`. Логика ПР2–ПР3 не переписывалась: модули перенесены, в сервис добавлена только `updateTask`, в представление — кнопка `edit`. Это подтвердило, что разделение ответственности между `task-service.js`, `form-validation.js`, `task-storage.js`, `task-view.js` и `main.js` выбрано верно: расширение потребовало точечных изменений, а не переработки.

Главный результат — понимание, что валидация не бывает одноуровневой. HTML-ограничения дают быструю проверку структуры, но не знают предметной области: `required` пропускает строку из пробелов и не проверяет уникальность `id`. Прикладная проверка в `validateTaskDraft` дополняет её правилами модели, а сервисные функции защищают данные независимо от формы. Отдельно разобрана работа с `localStorage`: хранилище принимает только строки, а успешный `JSON.parse` не гарантирует корректность схемы, поэтому данные проверяются полностью, а ошибка одной записи отклоняет весь список ради безопасного fallback к исходному набору.

Наиболее показательные ошибки при отладке — поле `disabled` не попадает в `FormData` (в режиме редактирования `FormData.get("id")` возвращает `null`, поэтому источником истины служит `editingId`) и пропущенный вызов `isValidPriority(priority)` вместо ссылки `isValidPriority`, из-за которого проверка приоритета молча пропускала некорректные значения. В итоге все обязательные проверки — 35 сервисных, 27 модульных и 23 браузерных — проходят без ошибок, индивидуальный вариант проверен, а три собственных сценария покрывают границу формы, восстановление после перезагрузки и повреждённое хранилище.
